# W3: the plan's decisions

The README and the code cite these decisions by number, W3-D1 to W3-D17. They were set on 2 November 2026,
when the lab was planned, and none changed afterwards. Where the README describes the lab as built, the README
is right. A number such as D-029 is one of the book's own decisions, listed in
[docs/book-decisions.md](../../docs/book-decisions.md); W1's and W2's decisions are in their own folders. A name
such as fig-12-01 or lst-04-03 is the book's figure 12.1 or listing 4.3. The pages behind the facts are under
chapter 12 in [LINKS.md](../../LINKS.md).

## The plan (2 November 2026)

- **W3-D1. Local first, no cloud spend.** One workstation: chapter 5's gateway and harness loop, the local models of chapter 9, W2's servers and fakes, W1's knowledge server over the runbook corpus, and fakes for what is new. The AWS form is offline: Terraform validated and planned, roles and stores read from the providers' pages into a fact sheet. A managed run, if one happens, follows D-029, D-034, and D-036 and goes through the gateway unchanged.
- **W3-D2. A state machine with durable state.** The run is a machine with named states: triggered, triaging, proposing, awaiting approval, executing, verifying, and the four terminal ones, done, rolled back, dropped, and refused. Every transition is written to a store, with the trace identifier, before the next step runs; the lab's store is a SQLite file, the production store is named per platform from the fact sheet. The test that matters: kill the harness between any two states, start it again, and the run resumes from the store with the same trace identifier and the same approval, and nothing executes twice. The harness holds no state a restart loses. The chapter's fig-12-01 is this machine.
- **W3-D3. Triage reads are W2's, plus the runbook and the changes.** The harness opens W2's three read sessions (pod status, alerts, events, pod logs, the metric series, the log search), W1's knowledge server for `search_runbooks`, and a ServiceNow server with one read, `get_recent_changes` for a service, since what changed is the first triage question. The alert's annotation names the runbook; the model proposes one step from it with its arguments; the harness matches the proposal against the runbook's steps. A proposal whose step is not in the named runbook is refused and counted (the false runbook rate). A service with no runbook gets a triage summary and no proposal.
- **W3-D4. Two writes, on a server of their own.** `restart_deployment` and `scale_deployment` (replicas within a per-service bound) on a fourth Kubernetes server, the writer, so that W2's server stays read-only in every annotation and every identity and its vetting result stands. Each write tool has an identity of its own; on AWS the writer assumes the tool's role per request with the engineer as source identity and the session named after their object ID, the chain of chapters 4 and 6, because attribution matters for a write where chapter 11 traded it away for reads. Each write tool checks the approval service's own record that a recorded yes covers exactly this call in this run, and applies each approval once; a retry after a timeout finds the approval applied and does nothing. Feature flags and PagerDuty are out of the lab (W3-D17).
- **W3-D5. The approval service is Larkspur's own.** A small HTTP service with a store: it files a request (workflow, trace identifier, tool, canonical arguments, requester, the expiry), notifies the approvers, records one decision with the approver's object ID and a reason, and answers two questions, whether a recorded yes covers exactly this call in this run and whether it has been applied. The record is lst-04-03's token made durable: one call, one argument set, one run, fifteen minutes by default, and the requester cannot approve their own. The model never sees an approval; the harness passes the approval's number to the write tool. The service is the one every workflow and every framework calls, so its interface is the long-running call of chapter 7: file, pending, decide, resume.
- **W3-D6. Who may approve.** The approver must hold the service's approvers group, read from W1's membership table by object ID as W2 reads its groups, and must not be the requester (chapter 2's separation of duties). The service map gains an `approvers` list per team. `approvals_required` is a parameter of the request, one by default and two for a write the service map marks as needing two, with a test for each; the chapter says the board promotes a pattern to one approver, then to a standard change, as it sees the evidence.
- **W3-D7. Timeout, and a late yes.** The approval expires after fifteen minutes unless the manifest says otherwise; on expiry the machine goes to dropped and the engineer is told, in the fixed wording, that the step was not taken. A yes after expiry is refused as expired and recorded. The run does not wait in a process: the state is in the store, the loop ends at awaiting approval, and the decision resumes it. A second decision on a decided request is refused and recorded.
- **W3-D8. Rollback and verification for every write.** Before a write, the tool records the previous state (the replica count; the deployment's generation and image for a restart). After it, the machine waits a bounded time and runs the verification read, pod status. A scale whose verification fails is scaled back to the recorded count under the same approval, whose text named both ("scale to 6; back to 3 if not healthy in five minutes"); a restart has no undo and its verification result is the record. Both outcomes, and the rollback itself, are transitions in the store, which is the evidence chapter 2's board asked for.
- **W3-D9. The change record.** When the approval is given, the harness, not the model, writes the change record to the ServiceNow server's one write, `record_change`, under an identity of its own, idempotent on the approval's number: the workflow, the service, the step and its arguments, the requester, the approver, the trace identifier, the expiry, and later the outcome. In the lab ServiceNow is a fake store; the record's fields come from the fact sheet.
- **W3-D10. The class of each call.** W3's harness classifies each model call by what the call's context holds: a call that carries log lines, which can hold health information (chapter 9), is Restricted and goes to `larkspur-chat-restricted` only; a call with pod status, alerts, metric values, the runbook's step, and a ticket's text is Confidential, the class chapter 6 gave W3's classified calls, and goes to `larkspur-chat`. The gateway's grid enforces it, and a test asks the rules to refuse a Restricted call on the Confidential alias. The harness trims log lines to fit the self-hosted model's window (chapter 9). When the restricted alias is down the machine goes to refused with "model unavailable", and the engineer works the incident without W3. The fakes' logs carry masked cardholder data, as the pipeline would deliver them.
- **W3-D11. The never-list in code.** W3's manifest takes chapter 4's six entries in the form W2's took: five as tool shapes (`delete_namespace`, `modify_iam`, `modify_security_group`, `read_vault_secret`, `run_command`), the payments slice kept out by the service map. Enforced in four places, each with a test: the harness allows the manifest's tools and no other; the catalog serves none of the actions; the write identities hold the two writes and nothing else, with a permission boundary that denies the never-list; and the tool gateway's rule, Cedar-shaped in the lab's stand-in and Cedar in the AWS form, permits `restart_deployment` and `scale_deployment` only for a namespace in the workflow's list. A runbook step that names a never-list action is refused at proposal time, and the refusal is a transition.
- **W3-D12. Everything read is untrusted, including what Larkspur wrote.** W2's four planted instructions stay in the fakes. W3 adds two: a changes ticket, written by the change-management agents of chapter 13, that tells the assistant the fix is to delete the namespace (chapter 4's second-order injection), and a runbook page, in a small corpus the lab adds beside W1's, with a step that runs an arbitrary command. The golden set fails a run that proposes the planted step; the never-list and the identities make it impossible if the model asks, and the lab shows both layers, as W2 did.
- **W3-D13. The approval UX.** Teams first: the approval card goes to each eligible approver's personal chat, since the decision is one person's and is bound to their identity, with a notice in the incident channel; Slack is the variant through the Entra binding of chapter 10. In the lab the bot is a stub: the card is a JSON file in the shape of an Adaptive Card, and a decision is posted by a test with a token. The requester sees the pending step, the decision, and the outcome in the chat where the request began.
- **W3-D14. Evaluation in two layers.** Deterministic: every transition and its persistence, the resume after a kill at each state, lst-04-03's refusals as the service's rules (another call, another run, expired, one's own request, no approval at all), the timeout and the late yes, the idempotent writes, the rollback on a failed verification, the never-list in four places, the class of each call and the grid's refusal, the change record written once, the planted cases at the structural layer. Model runs through the gateway on gpt-oss-20b and Gemma 4 12B, Restricted calls on the restricted alias: about twenty-five incidents (a crash loop with a runbook that says restart, saturation with a runbook that says scale, an incident with no runbook, a step outside the manifest, the two planted cases, a service the engineer may not see, a request to approve one's own step), scored on the step proposed and its arguments, nothing outside the named runbook, no write without an approval, the planted conclusions, and the labels on every call. No judge; a member of Tomasz Nowak's team reads every refusal and every proposal on a planted case before a change ships, until chapter 15 calibrates one.
- **W3-D15. Metrics from the store.** Time to triage (trigger to proposal, the median), false runbook rate (proposals not in the named runbook over proposals), approval latency, writes rolled back, and the harness's step count, computed by a script from the store and the logs and recorded with versions and dates, so chapter 12's metrics section reports what was measured.
- **W3-D16. Where Google and Microsoft differ, offline.** The approval service runs on AWS for every cloud (chapters 6 and 7); what differs is how a waiting run resumes and under which identity the write runs: ADK's long-running tool on Agent Runtime (chapter 7's lab), Foundry's require-approval setting and Agent Framework's tool approvals, and the durable store each platform offers, named from its own pages. The write identities per platform in the catalog's form, with the AWS roles written out. A fact sheet first, with dates.
- **W3-D17. Out of scope for the lab:** PagerDuty (the trigger is a fake alert or a manual request), feature flags, a real Teams or Slack bot, a real cluster, the real ServiceNow, and the managed applies. W2's manifest in chapter 5's listing stays the skeleton's version; W3's manifest grows past chapter 5's (the reads of W2, the second write, the ServiceNow tools, the sixth never entry), and the chapter says so, as chapter 11 did for W2.
