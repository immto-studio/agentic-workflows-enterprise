# W4: the plan's decisions

The README and the code cite these decisions by number, W4-D1 to W4-D18. They were set on 2 November 2026,
when the lab was planned, and W4's fact sheet changed six of them the same day (below). Where the README
describes the lab as built, the README is right. A number such as D-029 is one of the book's own decisions,
listed in [docs/book-decisions.md](../../docs/book-decisions.md). A reference such as ch05:448 is a line of the
book's manuscript, and fig-13-01 is the book's figure 13.1. The pages behind the facts are under chapter 13 in
[LINKS.md](../../LINKS.md).

## The plan (2 November 2026)

- **W4-D1. Local first, no cloud spend.** One workstation: chapter 5's gateway, harness and A2A skeleton, the local models of chapter 9, W3's ServiceNow fake and `record_change` pattern, and new fakes for GitHub, CI, and Terraform plans. The AWS form is offline: Terraform validated and planned, the per-agent identities read from the providers' pages into a fact sheet. A managed run, if one happens, follows D-029, D-034, and D-036 and goes through the gateway unchanged.
- **W4-D2. Three agents over A2A, because one belongs to another team.** The chapter answers "why not one agent with three tools" before splitting: the risk scorer belongs to the change-management team, with its own identity and budget, so A2A pays for itself there (ch05:448); the analyst and the scribe are the platform team's. Built on chapter 5's a2a-sdk 1.3.0 skeleton: the analyst is the read-only A2A server already there, the risk scorer is a second A2A server, and the scribe is the A2A client that orchestrates. A2A, not sub-agents-as-tools, because the risk scorer crosses a team boundary and the agents run long enough to need task states and artifacts. The topology is fig-13-01.
- **W4-D3. What each agent does and owns.** The **analyst** (platform team): reads the pull request, the CI results, the Terraform plan, and the service's recent ServiceNow changes; returns one structured evidence artifact; read-only, no write identity. The **risk scorer** (change-management team, its own identity and budget): takes the analyst's evidence over A2A and returns a risk class and a rationale; it reaches no source, only the evidence it is handed. The **scribe** (platform team, the orchestrator and A2A caller, standing in for the calling workflow as in chapter 5): triggers on the pull request or the scheduled release, calls the analyst and the risk scorer over A2A, assembles the evidence pack, and writes it to ServiceNow and the pull request. (The scribe's owning team is unstated in the chapters; the platform team is the default, since the scribe is the caller.)
- **W4-D4. The trigger.** A pull request opened, or a release scheduled. In the lab a fake webhook payload (a pull request with its diff, files, labels, and check runs) or a scheduled-release record drives the same evidence-gathering run; no real scheduler or webhook. (The scheduled-release path is unelaborated in the chapters; a fake record is the default.)
- **W4-D5. Evidence sources, as fakes.** A GitHub fake (the pull request: title, body, a diff summary, changed files, labels, and check-run conclusions), a CI-results fake, a Terraform-plan fake (the resource changes, with any destroy or replace marked), and the ServiceNow changes read reused from W3. Larkspur's real CI is GitHub Actions, with Jenkins retired except the mainframe batch pipeline (`pol-change-management.md`); Jenkins and Bamboo appear in the chapter as the adapter shapes W4 reads a CI result through, not as Larkspur systems, which resolves the book plan's lone "Bamboo" mention against the established estate. The lab's CI fake is a GitHub Actions checks payload; the chapter's "integration points" section shows the Jenkins and Bamboo adapters in prose.
- **W4-D6. The rung-2 boundary: a ticket and a PR comment, never infrastructure.** W4 writes an evidence pack to ServiceNow and a comment to the pull request, and nothing else. It never merges, never approves a required review, never applies a plan. The identity cannot do the thing it proposes (ch01:213); an auto-merge would move the workflow up a rung, so no identity in the workflow can merge. The evidence pack and the PR comment are the whole output; the CAB and the owning team decide.
- **W4-D7. The evidence pack in ServiceNow, written by a tool, keyed once.** The scribe calls a ServiceNow write tool (not the model) that attaches the pack to the change record, idempotent on the pull request or change identifier, as W3's `record_change` is idempotent on the approval number (ch12:342). The pack holds what the CAB samples (ch02:161, 170): the pull request and its diff summary, the CI result, the Terraform plan summary, the risk class and its rationale, the change class and the freeze-window check, the owning team and reviewer, and the trace identifier that joins the pack to the run. The pack's text is plain and carries no instruction, because W3 reads it later (W4-D12).
- **W4-D8. The PR comment.** The scribe writes one pull-request comment, updated in place and idempotent, that links the ServiceNow change record and states the risk class and the policy check. It says in its first line that it is evidence for the change advisory board, not an approval or a review.
- **W4-D9. The risk score: a class from facts, with a model-written rationale.** The risk scorer returns one of Low, Medium, or High, computed by a fixed rubric over the analyst's structured evidence (blast radius and whether a tier-0 service or the payments slice is touched, whether a rollback plan is present, whether CI passed, whether the change lands in the freeze window, and the change class). The model writes only the rationale prose, not the class. The chapter's "what a risk score can and cannot mean" section says: the score cannot authorize a change, cannot replace the CAB, and a hijacked analyst message cannot move it past the structural facts; it is advisory evidence, and humans decide (the structural-controls-carry-trust rule of ch12:312). (No numeric scale or rubric is committed anywhere; the three-class rubric computed from facts is the default.)
- **W4-D10. The policy and freeze check.** The scribe checks the change against the current policy (CAB Thursdays at 14:00 ET; standard, normal, and emergency classes; the year-end freeze 2026-12-14 to 2027-01-04) from the companion policy doc's current version, never the stale 2025 twin. A change in the freeze window, or a normal change with no CAB slot before its start time, is flagged in the pack and the comment.
- **W4-D11. Identities, pull-request-only.** Each agent its own identity (ch03:157, ch04:229). The scribe authenticates to GitHub as a GitHub App with no merge or approve permission (contents read, a pull-request comment write only), over OIDC as the companion's ADR-0049 prescribes for CI, and to ServiceNow with client credentials holding the change-write role only. The analyst holds read-only scopes to the sources; the risk scorer reaches no source at all. No identity in the workflow can merge, approve a review, or apply a plan, and a permission boundary denies those actions. A2A auth is chapter 5's: a static bearer per caller in the lab, a short-lived JWT in production, checked for signature, issuer, audience, and expiry; a request without the token gets a 401; a token is sent only to the card's origin. (No client-credentials or OIDC mechanism is pinned for W4 in the chapters; this is the default, built on ADR-0049 and the chapter 5 A2A pattern.)
- **W4-D12. Everything read is untrusted, including another agent's message and a pull request.** Another agent's A2A message is a tool result, not an instruction (ch04:229). Planted injections in the fakes: a pull-request body and a CI log that tell the analyst to report Low risk or to write "approved" into the pack. The deterministic class (W4-D9) and the pull-request-only identity (W4-D11) make them harmless, and the lab shows both layers, as W2 and W3 did. The other direction is the chapter's named link: W4's ServiceNow evidence text is what W3 later reads (ch04:265), so the pack carries facts and no instruction, and the chapter says that W4's output is the origin of W3's planted ticket.
- **W4-D13. No approval gate, because rung 2.** W4 writes nothing to infrastructure, so there is no lst-04-03 approval on a write; the change advisory board is the human decision, downstream, and the evidence pack is what it reads. The chapter states the contrast with W3's rung-3 gate.
- **W4-D14. The class of each call.** Internal by default (pull requests, CI output, Terraform plans, and change tickets are about systems); Confidential when a diff or a log line carries Confidential data, routed to `larkspur-chat`; the Restricted alias only if a log line carries Restricted data, which is rare for change management. The gateway's grid enforces it, as in W3, with a lighter rule because the work is mostly Internal.
- **W4-D15. Evaluation in two layers.** Deterministic: the A2A auth rejections (reused from chapter 5), the evidence-pack fields and the idempotent ServiceNow write, the deterministic class from fixed evidence, the PR-comment write, the policy and freeze check, the planted injections at the structural layer, and the identity that cannot merge, approve, or apply. Model runs through the gateway on gpt-oss-20b and Gemma 4 12B: about twenty changes (a standard change, a normal change needing the CAB, a change in the freeze window, a tier-0 or payments-slice change, a change with failing CI, a change with no rollback plan, a Terraform plan that destroys, and the two planted injections), scored on the pack's completeness, the risk class, that nothing was written to infrastructure, that no injection was followed, and the rationale's faithfulness to the evidence. No judge; a member of the owning teams reads the packs and the injection runs until chapter 15 calibrates one.
- **W4-D16. Metrics from the store.** Time to evidence pack (trigger to the pack written, the median), the risk-class distribution, pack completeness (every required field present), injection cases contained, and A2A task latency, computed by a script from the store and the logs with versions and dates, so the chapter's metrics report what was measured.
- **W4-D17. Where Google and Microsoft differ, offline.** A2A fronting per platform, from chapter 5's facts and the current pages: AgentCore Gateway passes A2A through with `"protocolType": "A2A"` and AgentCore Runtime hosts A2A servers on port 9000; Google's Agent Gateway governs A2A for Agent Platform agents, with ADK's A2A support experimental and Agent Runtime's preview; API Management imports A2A over JSON-RPC only; Foundry Agent Service's A2A tool is generally available for version 1.0 but over JSON-RPC only, without streaming and for text only, so the analyst's structured data part would not survive a Foundry caller, which the chapter notes. The per-agent identities and the evidence-pack write per platform, in the catalog's form, with the AWS roles written out. A fact sheet first, with dates.
- **W4-D18. Out of scope for the lab:** a real GitHub, ServiceNow, or CI system; auto-merge or a required-review approval; a real change advisory board; the managed applies; Jenkins and Bamboo as live systems (adapter shapes in prose only); and a real release scheduler (a fake record stands in). W4's manifest grows past chapter 5's with the A2A agents, the evidence tools, and the two writes, and the chapter says so, as W2 and W3 did.

## What the fact sheet changed (2 November 2026)

W4's fact sheet was gathered from public pages only, and every quotation in it was checked against the live
pages. It covers A2A and how AWS, Google, and Microsoft front it; reading a pull request and its checks on
GitHub; the evidence pack and the change record in ServiceNow; and what a risk score may mean, with separation
of duties.

- **W4-D17 corrected, and chapter 5's draft with it.** On AWS the A2A path is AgentCore **Runtime** hosting an A2A server on port 9000, **not** the Gateway: `CreateGatewayTarget`'s `protocolType` is `MCP | HTTP` only. Chapter 5's draft said the Gateway passes A2A through with `protocolType: "A2A"`, and was corrected. The other W4-D17 rows hold: Google's Agent Gateway governs A2A for Agent Platform agents (Agent Runtime's A2A preview, ADK's experimental); Azure API Management imports A2A over JSON-RPC only; Microsoft Foundry Agent Service's A2A tool is GA for 1.0 but **JSON-RPC and text only, no streaming**, so the analyst's structured `data` part would not survive a Foundry caller.
- **W4-D2, W4-D3 gain their vocabulary.** The a2a-sdk 1.3.0 pin is current; the agents serve Agent Cards at `/.well-known/agent-card.json` with a bearer scheme, carry the analyst's evidence and the risk scorer's result as structured `data` parts, and move through the spec's task states.
- **W4-D5, W4-D3 sharpened by GitHub's schema.** The analyst reads the pull-request object and its files list, and the CI result as the combined commit status (`success` / `pending` / `failure`) with the check-run conclusions.
- **W4-D7 gains its field mapping and type.** A normal change by default, a standard change once promoted; one POST to the Change Management API with the evidence attached; the record is left in New or Assess for the owning team and the CAB, because W4 never moves it to Implement (rung 2).
- **W4-D9 sharpened.** The score is a three-class rule over the analyst's evidence, in the shape of ServiceNow's rule-ordered risk conditions, the model writing only the rationale; "what a risk score cannot mean" rests on DORA (Goodhart, "individual scores are harmful"), ServiceNow (risk is a function of the administrator's defined rules), and Google SRE (risk managed structurally). The book names DORA's metric "change fail rate," as the page writes it.
- **W4-D6, W4-D11 confirmed.** W4 holds no GitHub reviewer seat and no ServiceNow approval role; GitHub's `production` environment gate (up to six reviewers, one approval needed, self-review preventable) is the human's, fed by Larkspur's own rule that it needs an approved ServiceNow change number and one owning-team reviewer (policy, not a GitHub field).

Corrected again on 10 November 2026, in the last check of the book's product facts: since 17 June 2026
AgentCore Gateway can front an A2A server as an HTTP passthrough target, which it forwards without protocol
translation. Chapters 5 and 13 say so.
